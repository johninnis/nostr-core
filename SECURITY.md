# Security

This document describes the security properties `innis/nostr-core` provides, the properties it deliberately does not provide, and the reasoning behind the non-obvious design decisions. It is the reference consumers should read before relying on this library in production, and the reference contributors should read before changing any of the cryptographic, identity, or HTTP-facing code paths.

## Audit status

**This library has not undergone an independent third-party cryptographic audit.** It is built and reviewed with care — strict layer separation, conformance against the official BIP-340 and NIP-44 test vectors, cross-engine property sweeps, and the design decisions recorded below and in [`docs/adr/`](docs/adr/) — but internal review is not a substitute for an external audit. Nostr keys frequently control real value (zaps, Cashu/nutzaps), so treat the cryptographic guarantees as best-effort and not externally verified. Use the library at your own risk, weigh the consumer responsibilities set out below, and prefer the native `libsecp256k1` (FFI) path for any server-side or high-value signer. If you commission or perform an audit, please share the results through the vulnerability-reporting channel below.

## Reporting a vulnerability

If you have found a security vulnerability in `innis/nostr-core`, report it privately through GitHub's built-in vulnerability reporting: **Security → Advisories → Report a vulnerability** on the repository page. Do not open a public issue for security-sensitive bugs.

Include:

- A description of the vulnerability and its impact.
- Reproduction steps or a proof-of-concept.
- The affected version (tag or commit SHA).

Acknowledgement is best-effort within 72 hours. Fixes land first, then the advisory is published.

For non-security bugs (typos, error-message tweaks, parsing issues that do not affect crypto), open a regular issue.

This project does not run a bug bounty.

## Supported versions

Only the latest tagged release is supported. Older releases do not receive backported fixes, ever. Use the latest version.

## Security properties

### What this library provides

- **BIP-340 Schnorr signing and verification** via `Secp256k1Signer`. The FFI path uses the system `libsecp256k1` C library when available; the pure-PHP path uses `paragonie/ecc` as a fallback. Both paths produce byte-identical signatures under identical `aux_rand`, validated against the BIP-340 specification vectors for Nostr's 32-byte event-id messages and a 100-iteration cross-engine property sweep. Signing rejects any message that is not exactly 32 bytes (`InvalidArgumentException`): every Nostr signature is over a `SHA-256` event id, so a wrong-length message is a programmer error rather than a request to sign arbitrary data. See [ADR 0013](docs/adr/0013-secp256k1signer-sign-rejects-non-32-byte-messages.md).

- **NIP-44 v2 authenticated encryption.** `Nip44Cipher` implements the official NIP-44 v2 spec: ChaCha20 with HMAC-SHA256 MAC; MAC verification happens before unpadding (no padding oracle); nonces come from an injected `RandomBytesGeneratorInterface`. Covered by the official NIP-44 test vectors and a 200-iteration property fuzz that includes ciphertext-tamper and MAC-tamper rejection. A plaintext is 1 to 262144 bytes by default, a maximum the host can raise to NIP-44's own 4294967295, with the six-byte length prefix from 65536; `decrypt` refuses a payload longer than that maximum produces before decoding it (see [ADR 0117](docs/adr/0117-nip-44-carries-the-extended-length-prefix-up-to-a-configurable-maximum-that-defaults.md)).

- **NIP-44 ECDH with libsecp256k1 acceleration.** `Secp256k1Ecdh` mirrors the signature service: FFI when available, pure-PHP fallback otherwise. FFI and pure-PHP paths produce byte-identical shared-X values, validated by a 100-iteration parity sweep.

- **NIP-04 legacy encrypted messages — shipped, deprecated, and unauthenticated.** `Nip04Cipher` implements NIP-04 exactly as specified: AES-256-CBC over the raw 32-byte ECDH shared secret, serialised as `base64(ciphertext)?iv=base64(iv)`. Both `Nip04EncryptionInterface` methods carry `#[Deprecated]`. It is documented here precisely because it is the weakest primitive in the package and the one a reader is most likely to assume is protected the way its NIP-44 sibling above is. It is not.

    - **There is no MAC.** Ciphertext is malleable — a hostile relay or peer can flip plaintext bits by flipping ciphertext bits and nothing detects it. The NIP-44 property stated above, MAC verified before unpadding, has no NIP-04 equivalent, because there is no MAC to verify.
    - **Decryption is a padding oracle, and this library cannot close it.** With no MAC, a tampered payload whose PKCS#7 padding happens to be valid *decrypts successfully* and returns garbage plaintext, while one with invalid padding throws. The distinguishing signal is therefore the outcome itself, which no choice of error text can hide, and the timing of an early framing rejection differs from that of a full block-cipher pass. `decrypt` does report one indistinguishable message for every rejection ([ADR 0118](docs/adr/0118-nip04cipher-reports-one-indistinguishable-decryption-failure-bounds-its-payload.md)), which stops a consumer leaking *which stage* rejected a payload — but that narrows an information leak, it does not make the scheme authenticated. The oracle is a property of unauthenticated CBC and is closed only by not using NIP-04.
    - **Consumer responsibilities.** Do not expose NIP-04 decryption to untrusted input without rate limiting. Treat decrypt success-versus-failure as a sensitive signal — not a public API result, and not a per-attempt log line an attacker can observe. Use NIP-44 for anything new; NIP-04 is here for interoperability with existing kind-4 history, not because it is safe.
    - `decrypt` bounds the payload to 52–87472 bytes, so it cannot be made to buffer an unbounded frame, and `encrypt` refuses a plaintext over 65567 bytes, the largest whose payload fits that bound.

- **NIP-49 password-encrypted private keys.** `Nip49Cipher` uses scrypt + XChaCha20-Poly1305, NFKC password normalisation per spec, and treats the password as a `Closure(): string` so the plaintext does not persist in caller scope. Spec vectors verified. Encryption floors the scrypt work factor at `logN 16` so the library never mints a brute-forceable `ncryptsec`, while decryption still accepts weaker values for interoperability; see [ADR 0114](docs/adr/0114-nip-49-floors-what-it-encrypts-at-logn-16-and-bounds-what-it-decrypts-at-a-library.md). Unlike secp256k1 and NIP-44, NIP-49 has **no pure-PHP fallback**: scrypt over raw `(N, r, p)` is reached only through `ext-ffi` + libsodium, so on a `gmp`-only host NIP-49 throws rather than degrading. The asymmetry with the FFI-optional signing path is deliberate; see [ADR 0039](docs/adr/0039-nip49-scrypt-requires-ffi-with-no-pure-php-fallback.md). Rejecting a tampered key-security byte rather than mapping it to `Untracked` is what makes the AEAD's associated-data authentication detect tampering; see [ADR 0119](docs/adr/0119-an-unrecognised-key-security-byte-is-refused-when-the-ncryptsec-is-read-never-read.md).

- **Private-key scalar validation.** `PrivateKey::tryFromHex` / `tryFromBytes` / `tryFromBech32` reject a scalar that is zero or `>= n` (the curve order), and `generate()` only ever mints one in `[1, n-1]`. This keeps the native and pure-PHP signing backends in agreement — the native path rejects an out-of-range scalar while the pure-PHP path would otherwise silently reduce it mod `n` and build a degenerate or aliased key; see [ADR 0029](docs/adr/0029-privatekey-rejects-scalars-outside-the-curve-order.md).

- **NIP-59 gift-wrap.** `GiftWrapper` validates both outer and inner signatures before trusting any content, requires the seal to carry no tags but `expiration` tags holding a valid NIP-40 timestamp ([ADR 0133](docs/adr/0133-a-seal-carries-no-tags-but-expiration-tags.md)) and the decrypted rumour to be unsigned (per NIP-59) and the rumour's pubkey to match the seal author, returns a `GiftWrapUnwrapFailure` for a wrap it cannot open, forged or undecryptable rather than throwing, zeroes ephemeral keys it generates, and passes all `ConversationKey` material through the `expose(Closure)` lifecycle so derived secrets do not escape their use-site scope.

- **ECDH input validation.** The bundled `Secp256k1Ecdh` validates that the peer public key's x-coordinate lies in `(0, p)` and refuses an invalid secret scalar — on both the FFI and pure-PHP paths (the pure-PHP path sees one as a shared point at the identity) — before any shared secret is returned. `PrivateKey` already refuses a scalar outside `[1, n-1]`, so this is a defence behind that invariant. `ConversationKey::derive(...)` delegates the ECDH to the injected `EcdhServiceInterface`, so these checks live in that implementation; a consumer that supplies its own `EcdhServiceInterface` is responsible for the equivalent validation.

- **Secret material lifecycle.** `SecretKeyMaterial`, `PrivateKey`, and `ConversationKey` hold secrets behind an `expose(Closure)` contract. `expose` hands the closure a freshly-allocated copy of the bytes — not a copy-on-write alias of the stored secret — and `sodium_memzero`s that copy in a `finally`, so the bytes the closure read are actually wiped rather than left in a spared buffer (see [ADR 0028](docs/adr/0028-secretkeymaterial-expose-hands-a-detached-copy-so-the-wipe-is-effective.md)); a closure that copies the bytes into an escaping variable still owns wiping that copy. `zero()` deterministically erases the stored byte buffer and leaves the object in a state that throws `SecretKeyMaterialZeroedException` on any subsequent access. The pure-PHP sign and ECDH operations work on bytes and GMP integers, never hex: `Secp256k1Math::gmpToBytes` zeroes its working buffer in `try/finally`, and pure-PHP signing zeroes its own secret byte intermediates (the tweaked key, the nonce input and the nonce hash) inline. A GMP integer holding a secret cannot be wiped from PHP.

- **Defensive relay-protocol parsing.** `REQ` and `COUNT` messages carry one or more filters with no maximum, since how many a relay serves is its own policy (see [ADR 0125](docs/adr/0125-a-request-carries-any-number-of-filters-and-values-and-how-many-a-relay-serves.md)); `Filter` and `TagFilter` hold any number of values in each array-valued field, since how many a relay serves is likewise its policy, and a tag condition is named by one letter, so a filter holds at most 52 of them (see the relay-protocol parsing caps below); a filter that can match nothing is parsed as it is and matches nothing; `SubscriptionId` caps its length at 64 characters as NIP-01 does; `OkMessage` requires a strict boolean for its `accepted` flag and the message NIP-01 says must always be present, and `ClosedMessage` requires its message too. Malformed relay input is rejected as a typed outcome — the message `tryFromArray` and `tryFromJson` factories (`ClientMessage::tryFromJson` and `RelayMessage::tryFromJson` for a message of unknown type) return `null`, and the trusted `from…` constructors throw `InvalidArgumentException` — rather than propagating a `TypeError`. A parsed `Event` re-encodes its own fields on `toJson()` and never re-emits the input bytes, so keys and spellings the event did not verify are not relayed (see [ADR 0076](docs/adr/0076-an-event-serialises-its-fields-never-the-bytes-it-was-parsed-from.md)).

- **NIP-05 identifier parsing.** Strict charset validation on both the local part and domain. IP literals (IPv6, and any domain whose last label is a decimal or `0x` hexadecimal number, which a URL parser reads as IPv4: `127.1`, `0x7f.1`, `127.0x1`), hostnames with injected paths or user-info, and control characters are rejected at construction ([ADR 0091](docs/adr/0091-nip05identifier-trims-only-the-whole-input-and-rejects-a-local-part-outside-the-allowed.md)). This is syntax only: a hostname that resolves to a private address is refused by the HTTP adapter's check after DNS resolution ([ADR 0090](docs/adr/0090-the-host-hardens-the-transport-behind-httpserviceinterface-which-returns-the-raw-body.md)).

- **NIP-98 event validation.** `Nip98Validator` enforces kind, signature, timestamp-within-tolerance, NIP-40 expiry (an event any of whose `expiration` tags has passed is refused as `Expired`), URL match (both sides compared as canonical `HttpUrl` values, a `u` tag that is not an absolute http(s) URL reported as malformed), method match, and payload-hash consistency, and enforces single-use by recording each event id once through an injected `Nip98ReplayGuardInterface` (returning a `Replayed` failure if the same id is presented again within the replay window). The request's body hash is a `Sha256Hash`, parsed once as 64 lowercase hex characters, so a caller holding an upper-case hash is refused when it builds the value rather than having every valid event rejected as a mismatch; `Nip98Request::fromBody` computes it from the body. A non-empty body requires a `payload` tag equal to that hash exactly, an upper-case tag being a mismatch; an empty body forbids one, including a tag carrying the empty string's hash, and a caller who supplies the empty string's hash as the body hash has supplied no body (nostr-adrs ADR-0024). The `Authorization` scheme token is matched without regard to case, because RFC 9110 defines it that way and the token is public and proves nothing; everything after it is matched exactly. See [ADR 0073](docs/adr/0073-the-nostr-auth-scheme-token-is-matched-without-regard-to-case.md).

- **NIP-42 AUTH event validation.** `Nip42Validator` checks the kind, the timestamp against an injected clock, that the event names exactly one challenge equal to the one you issued, and that it names exactly one relay URL equal to yours. It returns a `Nip42ValidationFailure` rather than throwing. **It does not verify the signature**, deliberately: an AUTH event is validated as an event first, so a consumer must run `EventValidator` (or `Event::verify`) before trusting the pubkey the event claims. Wiring the NIP-42 validator without that step authenticates forged events. See [ADR 0127](docs/adr/0127-nip-42-is-checked-by-a-domain-checker-at-a-given-instant-and-the-validator-adds.md).

### What this library does not provide

These are load-bearing consumer responsibilities. The library deliberately does not handle them.

- **A durable NIP-98 replay store.** `Nip98Validator` enforces single-use by calling the injected `Nip98ReplayGuardInterface::recordOnce(...)`, but the durability, scope, and eviction of the seen-id store live in the consumer-supplied adapter. An in-memory guard only blocks replay within one process; a multi-node deployment needs a shared store. The replay window is `2t + 1` seconds for a timestamp tolerance of `t` (default `2 × 60 + 1 = 121` seconds), covering every second the tolerance check accepts; events older than that fall outside the tolerance check and are rejected before the replay guard is consulted.

- **SSRF mitigation, response-size limits, and redirect policy for NIP-05 and NIP-11 fetches.** Identifier validation rejects IP literals and syntactically invalid hostnames, but a hostname can resolve to any address, and the HTTP request itself is issued by the consumer-supplied `HttpServiceInterface` adapter. Refusing a private, loopback or link-local destination (RFC 1918, link-local and cloud metadata addresses included), checked on the address after DNS resolution and pinned for the connection, for a URL someone else names; never following a redirect (NIP-05 fetchers MUST ignore them, and the port reports one as `HttpFetchFailure::NoAnswer`), capping the response body so a hostile peer cannot stream gigabytes, and treating the timeout as a hard ceiling are the adapter's responsibility — the obligations are spelled out in [ADR 0090](docs/adr/0090-the-host-hardens-the-transport-behind-httpserviceinterface-which-returns-the-raw-body.md), which the fence on `HttpServiceInterface::get` points to. The adapter returns the body as it arrived; this library decodes it, and a body that is not a JSON object is no answer.

- **Rate limiting of NIP-49 decrypt attempts, and bounding scrypt memory.** Scrypt runs before AEAD authentication: the scrypt output *is* the AEAD key, so MAC verification cannot happen first. An adversarial `ncryptsec` forces a full scrypt derivation before rejection, and a high `logN` makes that derivation expensive (`logN 22` is roughly 4 GiB). Protect the decrypt entry point with rate limiting, and — where the `ncryptsec` is attacker-influenced — construct `Nip49Cipher` with a `Nip49WorkFactor` whose `maxDecryptLogN` ceiling is stricter (it defaults to 22, this library's own limit: NIP-49 sets no maximum, and an `ncryptsec` above 22 is refused, with `Nip49WorkFactorRefusedException` rather than the wrong-password `Nip49DecryptionFailedException`) to bound the per-call memory cost; see [ADR 0114](docs/adr/0114-nip-49-floors-what-it-encrypts-at-logn-16-and-bounds-what-it-decrypts-at-a-library.md).

- **Guarantees about memory state after operations.** The library calls `sodium_memzero` on secret-bearing string buffers it creates, as a defence-in-depth discipline. PHP's runtime makes internal copies (interned strings, OPcache, hash-table buckets, temporaries created by standard-library functions) that the library cannot see or clear. Treat memory hygiene as best-effort, not as a guarantee.

- **Destructor-based zeroing.** `SecretKeyMaterial::__destruct` calls `zero()` for defence in depth, but PHP's garbage collector runs on refcount-zero, which may never happen for objects captured in long-lived closures, static state, exception trace frames, or cyclic references. Applications requiring bounded key-material lifetimes must call `$privateKey->zero()` explicitly. Do not rely on the destructor.

- **Timing-side-channel resistance on the pure-PHP fallback path.** The pure-PHP signing, public-key derivation, and ECDH implementations (via `paragonie/ecc` over GMP) are not constant-time, and cannot be made so. The secret-dependent operations — scalar multiplication of the private key and the per-signature nonce, the modular arithmetic that builds `s`, and the ECDH `priv·P` — run on GMP big-integer arithmetic and an interpreted double-and-add point multiplication, both of which branch on the value of the secret; a garbage-collected interpreted runtime also gives no control over instruction timing or memory-access patterns. Mitigations (Montgomery ladder, scalar/nonce blinding) can reduce the leakage but not eliminate it, because they still run on variable-time GMP and the Zend engine — a true guarantee needs the secret-independent machine code that native `libsecp256k1` provides. A local or co-located attacker able to measure signing/ECDH timing could, in principle, recover private-key material. For any server-side or long-lived signer — a relay, a NIP-46 remote signer/bunker, or any service that repeatedly signs attacker-influenced messages with a fixed key — install `libsecp256k1`, enable the `ffi` extension, and verify the native path is active before deploying. PHP's default `ffi.enable=preload` allows FFI only on the CLI and in preloaded code, so under a non-CLI SAPI such as php-fpm the native path is silently unavailable — signing and ECDH fall back to the pure-PHP implementation, which is not constant-time, and NIP-49 throws — unless the host sets `ffi.enable=true` or preloads this library through `opcache.preload`. Verify it at runtime rather than by inspection: `Secp256k1Signer::backend()` and `Secp256k1Ecdh::backend()` return `Secp256k1Backend::Native` or `Secp256k1Backend::PurePhp` for the adapter instance you hold, so a signer that silently landed on the fallback — a DI definition passing `null`, or a host that lost the native library in an image rebuild — fails a startup assertion instead of running for months undetected. The pure-PHP fallback is intended for portability and low-exposure client use, not a hardened signing oracle. See [ADR 0101](docs/adr/0101-secp256k1-signing-and-ecdh-keep-a-native-ffi-path-and-a-pure-php-fallback-and-their.md).

- **The lifecycle of a NIP-42 challenge.** `Nip42Validator` matches an AUTH event against the challenge you give it and rejects one written outside its timestamp tolerance, but issuing a challenge, storing it against the connection it was sent to, expiring it and refusing a second use of it are the relay's. A validator handed the same challenge twice will accept the same event twice, exactly as its NIP-98 sibling would without a replay guard. `Challenge` cannot hold the empty string, so an unset challenge cannot compare equal to an absent one, and the comparison is constant time.

- **Authenticity of payment events (NIP-57 zaps, NIP-61 nutzaps).** `ZapReceipt::tryFromEvent` and `Nutzap::tryFromEvent` are **parsers, not verifiers**. Neither checks a signature. Anyone can publish a kind 9735 or kind 9321 event, so nothing these types return is trustworthy until the consumer has verified the event itself — and displaying an unverified one as "X sent you N sats" is a spoofing vector, not a display bug.

    - **`ZapReceipt` does not authenticate anything — use `ZapReceiptVerifier` for that.** `getSenderPubkey()` is the author of the zap request carried in the `description` tag, and is attacker-chosen until verified. `ZapReceipt::tryFromEvent` accepts only a receipt with exactly one `description` (a signed kind 9734 event) and one readable `bolt11`, and parses the request once, so the verifier and every other reader see the same request. `ZapReceiptVerifier::verify($receipt, $lnurlProviderPubkey, $expectedLnurl)` then applies NIP-57 Appendix F: the receipt's pubkey must equal the recipient's LNURL provider `nostrPubkey`, and the request's `lnurl` tag (when you supply an expected value) must match. It additionally verifies both the receipt's signature and the embedded zap request's own signature — the latter is not an Appendix F requirement, but without it the provider could attribute the zap to an arbitrary sender. See [ADR 0079](docs/adr/0079-a-zap-receipt-holds-the-one-zap-request-it-carries-and-verification-takes-the-receipt.md).
    - **You must supply the LNURL provider pubkey; it is the root of trust.** This package never fetches LNURL configuration, so it cannot discover that key — with the wrong one, a receipt from *any* provider verifies. Obtain it from the recipient's LNURL endpoint yourself. `ZapReceipt::tryFromEvent` also enforces one consistency rule on its own: the BOLT-11 amount is authoritative and it returns `null` when the request's `amount` tag disagrees, so a receipt cannot claim one figure in the invoice and another in the request — but that is a consistency check, not authentication.
    - **`Nutzap` does not verify a nutzap.** NIP-61 asks an observer to check that the recipient's `kind:10019` lists the mint, that each proof is P2PK-locked to the public key that event names, that the `u` tag is one of its mints, and that each proof's DLEQ proof verifies, and notes that "All these checks can be done offline" given the recipient's `kind:10019` and the mint's keyset. This package performs none of them: it parses the claimed proofs' amounts and unit. Whether a proof is still unspent is knowable only from the mint, which this package does not contact. Treat a parsed amount as a claim, not as funds. Its `getSenderPubkey()` is the event's own pubkey, which is authenticated **only if you verified the event signature first**.
    - **Verify before you trust.** Run `EventValidator::validateEvent()` (or `Event::verify()`) on any payment event before handing it to these types. Then, for a zap receipt, run `ZapReceiptVerifier::verify()` with the provider key, which applies the NIP-57 Appendix F check; for a nutzap, apply NIP-61's observer checks yourself. The parsers perform none of these steps and will not fail if you skip them.

- **Safety of PHP's native `unserialize()` on library types.** Value objects in this library are not designed to round-trip through PHP's native `serialize()` / `unserialize()` functions. `unserialize` bypasses constructor validation and can instantiate library types in states the normal constructors would reject. Do not pass untrusted data through `unserialize()` into any library type. Parse incoming JSON with `Event::tryFromJson` or `Filter::tryFromJson`, a whole relay or client message with `RelayMessage::tryFromJson` or `ClientMessage::tryFromJson`, or any other wire value with `JsonWireFormat::decode` and then the type's `tryFromArray`; those factories perform their own type validation. Never feed `json_decode` output to a `tryFromArray`: `json_decode($json, true)` reads `{}` and `[]` alike, so a JSON array where a filter object belongs would become `[]`, the filter that matches every event. See [ADR 0112](docs/adr/0112-a-decoded-json-object-is-kept-apart-from-a-json-array.md).

- **Transport-layer limits.** `ClientMessage::tryFromJson` and `RelayMessage::tryFromJson` decode through `JsonWireFormat::decode`, which `json_validate`s then `json_decode`s at a nesting-depth limit of 512 and applies no input-size cap. WebSocket-frame size limits belong in the transport layer, outside this library.

## Design decisions

### `::create()` factories over auto-probing constructors

`Secp256k1Signer` and `Secp256k1Ecdh` expose a static `create()` factory that probes for `libsecp256k1` and dispatches FFI or pure-PHP. The bare constructor stays on the pure-PHP path unless an FFI handle is passed explicitly. Constructors deliberately do not probe the system library, because a constructor that silently `dlopen`s a C library at construction time is a hidden dependency and a hidden failure mode. Keeping the probe in a named constructor makes the side effect opt-in and easy to reason about for tests and DI containers.

Consumer code should use `Secp256k1Signer::create()` and `Secp256k1Ecdh::create()`. The bare constructor is for dependency injection and for tests that need to force the pure-PHP path.

Because the probe is silent — a host without the native library gets a working signer on the weaker path — both adapters expose `backend(): Secp256k1Backend`, reporting `Native` or `PurePhp` for the instance you hold rather than re-probing the host. It is deliberately declared on the concrete adapters and not on `SignatureServiceInterface` / `EcdhServiceInterface`, so a composition root can assert on it while no domain or application code can branch cryptographic behaviour on it. Asserting, reporting, and logging are the sanctioned uses. Full rationale: [ADR 0101](docs/adr/0101-secp256k1-signing-and-ecdh-keep-a-native-ffi-path-and-a-pure-php-fallback-and-their.md).

### `zero()` is a contract, not a destructor guarantee

After `zero()`, every subsequent call on the material (and on the `PrivateKey` / `ConversationKey` wrapping it) throws `SecretKeyMaterialZeroedException`. The destructor calls `zero()` only as defence in depth — PHP frees on refcount zero, which may never happen for keys captured in closures, statics, or trace frames — so an application requiring deterministic key erasure (session-scoped or bunker-style signers) must call `$key->zero()` explicitly at end of life. Full rationale: [ADR 0015](docs/adr/0015-zero-is-a-contract-not-a-guarantee-via-destruction.md).

### NIP-49 password as `Closure(): string`

`Nip49EncryptionInterface::encrypt` and `::decrypt` take the password as a `Closure(): string` rather than a raw string. The adapter invokes the closure exactly once and `sodium_memzero`s both the revealed password and its NFKC-normalised copy on the way out. To make those wipes real rather than nominal, the revealed value is first detached into a buffer the adapter solely owns (`$revealed ^ str_repeat("\0", …)`): PHP strings are copy-on-write and `sodium_memzero` separates a shared string before writing, so wiping the provider's own return value would scrub a throwaway — the same trap [ADR 0028](docs/adr/0028-secretkeymaterial-expose-hands-a-detached-copy-so-the-wipe-is-effective.md) documents for `SecretKeyMaterial::expose`.

**This wipes the library's copy, not yours.** If your closure returns a variable you still hold — `static fn (): string => $password` — that binding is untouched and remains readable after the call; this is verifiable in a few lines and is not something the library can change, since the buffer is yours. The `Closure` shape pays off only when it *produces* the password without the caller retaining it: reading a prompt, unsealing it from a keystore, or decrypting it on demand. If you do keep the password in scope, zero it yourself. The alternative of accepting a raw `string` would be strictly worse — the value would then always be aliased in the caller's frame — but the closure is not a substitute for the caller managing its own secret.

### Strict 64-byte signatures

`Signature::tryFromHex` accepts only a complete 64-byte signature (exactly 128 lowercase hex characters) and returns `null` for anything shorter, longer, upper-case, or non-hex — it never zero-pads a short input, which could fabricate the wrong signature when the missing bytes came from `s`. If interoperability with leading-zero-stripping producers is ever required, it belongs in a verify-and-pick step above the value object. Full rationale: [ADR 0026](docs/adr/0026-signature-tryfromhex-requires-a-full-64-byte-signature.md).

### NIP-44 nonce injection via `RandomBytesGeneratorInterface`

`Nip44Cipher` has no public `encryptWithNonce`; nonces come from an injected `RandomBytesGeneratorInterface` (default `NativeRandomBytesGenerator`; a deterministic generator in tests), so a caller cannot supply a reused nonce — a footgun that breaks ChaCha20 confidentiality catastrophically. The same pattern covers `Nip49Cipher`'s salt and nonce generation. Full rationale: [ADR 0014](docs/adr/0014-nip44cipher-has-no-public-encryptwithnonce.md).

### Each secret wrapper owns a fresh `SecretKeyMaterial`

`PrivateKey::tryFromBytes` and `ConversationKey::tryFromBytes` each allocate their own `SecretKeyMaterial` (via `SecretKeyMaterial::tryFromBytes`, which validates the length and returns `null` on a wrong size). A wrapping type therefore owns the buffer it zeroes: calling `zero()` on one `PrivateKey` cannot silently wipe the key material held by another object, because no API hands the same material instance to two wrappers. `SecretKeyMaterial`'s named constructors (`fromBytes`, `tryFromBytes`, `tryFromHex`, `random`) are public; the lifecycle safety comes from each wrapper allocating a distinct material, not from hiding the factory.

### Gift-wrap outer signature verified, not merely present

`GiftWrapper::unwrap` cryptographically `verify()`s the outer wrap rather than trusting that it merely carries a signature. A gift-wrap `Event` always holds a well-formed signature by construction, but that guarantees only that a signature is present and correctly shaped — not that it is valid over the wrap's fields. NIP-44's AEAD MAC catches ciphertext tampering on its own, but a malicious relay or man-in-the-middle could still modify the outer wrap's non-content fields (tags, `created_at`, claimed pubkey) without the MAC firing. The outer `verify()` closes that gap.

### NIP-05 domain charset rejects IP literals

`Nip05Identifier::tryFromString` enforces a strict DNS-hostname pattern on the domain (lowercase alphanumerics, hyphens, dots, at least one label separator), which refuses an IPv6 literal, and refuses a domain whose last label is a decimal or `0x` hexadecimal number, which refuses an IPv4 literal in every spelling the WHATWG URL parser accepts (`127.0.0.1`, `127.1`, `0x7f.1`, `127.0x1`). It does not reject a hostname that resolves to a private or loopback address (for example `intranet.local`, or a public name pointed at `127.0.0.1`): only the resolved address shows that, so the HTTP adapter refuses it after DNS resolution and pins it for the connection ([ADR 0090](docs/adr/0090-the-host-hardens-the-transport-behind-httpserviceinterface-which-returns-the-raw-body.md)). Splitting the concerns keeps the identifier type syntactically strict and the HTTP adapter semantically responsible.

### `Nip11Info` returns `null` for malformed fields

`Nip11Info`'s lazy accessors type-guard the data they read. A relay returning `"supported_nips": "not-an-array"` causes `getSupportedNips()` to return `null` rather than propagating a `TypeError` to the caller. Relays are untrusted peers; graceful degradation on malformed responses is preferable to exception-based denial of service.

### `Secp256k1Signer::verify` is a total predicate

`verify` catches `Throwable` and returns `false`: it is called per event on untrusted data by relays, so a throwing verifier would be a denial-of-service vector, and "not valid" is the safe verdict for any input it cannot positively verify. This is a deliberate, bounded exception to "never swallow an exception" — unlike `sign`, which throws on a wrong-length message (a programmer error on trusted input). Full rationale: [ADR 0027](docs/adr/0027-secp256k1signer-verify-is-a-total-predicate.md).

### Relay-protocol parsing caps

`REQ` and `COUNT` carry one or more filters and set no maximum: NIP-01 sets none, and a relay limits the filters it serves as its own configurable policy, refused with a `CLOSED` and advertised as NIP-11 `max_filters` ([ADR 0125](docs/adr/0125-a-request-carries-any-number-of-filters-and-values-and-how-many-a-relay-serves.md)). `Filter` sets no maximum on the values in an array-valued field, as NIP-01 sets none, nor on its `limit` field, which a relay clamps to its own NIP-11 `max_limit` ([ADR 0102](docs/adr/0102-filter-refuses-only-a-negative-limit-never-clamps-it-and-the-ceiling-is-relay-policy.md)); `TagFilter` refuses a `#` key that is not one letter `a`–`z` or `A`–`Z`, on both the `fromValues` and `tryFromArray` paths. A filter must be a JSON object: a JSON list, the empty one included, is refused on the wire rather than parsed as the empty filter, which would match every event; only `{}` is that filter (see [ADR 0112](docs/adr/0112-a-decoded-json-object-is-kept-apart-from-a-json-array.md)). `SubscriptionId` is capped at 64 Unicode characters, the NIP-01 limit, and must be valid UTF-8; it is otherwise arbitrary, so a host that logs or renders one escapes it.

**These are per-field bounds, not a bound on the frame.** A filter may name up to 52 tag conditions, one per letter NIP-01 allows, and each holds any number of values, so one `REQ` can present tens of thousands of values, bounded only by the frame that carries it. `TagFilter::matches()` iterates one index entry per tag name for every candidate event, so both the memory a filter pins and the per-event matching cost scale with counts the client chooses. Bounding total request size is the transport's job (see the transport-layer limits note above), and a relay that wants a ceiling on tag-name count or total filter values must impose it in the layer that owns its resource policy.

### Memzero is a discipline, not a tested contract

Pure-PHP signing and ECDH contain explicit `sodium_memzero` calls on every byte intermediate that briefly holds secret material; they hold no hex intermediates. These calls are a defence-in-depth discipline, not a tested contract. Writing a test that asserts the memzero calls fire with the expected sequence and lengths is possible (via a namespace-scoped function override) but has narrow value: it would protect a fallback code path that is not the hot path in any production deployment, against the specific regression of someone deleting a `sodium_memzero` line during a refactor. The existing byte-identical BIP-340 vectors, cross-engine property sweeps, and NIP-44 property fuzz give stronger correctness guarantees for the paths that matter. If the pure-PHP path ever becomes primary, the memzero-contract spy is the regression guard to add.
